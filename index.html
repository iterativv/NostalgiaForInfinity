Freqtrade Bot Report

In-browser port of tools/bot_report.py — exports a redacted JSON telemetry report from a running freqtrade REST API, so strategy developers can review how a strategy behaves in production. Everything runs locally in this browser tab.

No server sees your data

This page is a single static file with all logic embedded. It makes no network call to any server except the freqtrade API URL you enter below. There is no CDN, no fonts, no analytics and no uploads, nothing stored: the report is generated in your browser and saved straight to your disk. Closing the tab discards everything, including your credentials. Your browser's own password manager may offer to save the login for convenience — that storage belongs to the browser, not this page.

You can verify this: press F12 to open your browser DevTools, switch to the Network tab, and reload this page. You will see zero requests until you click Export report, and afterwards only requests to your bot's address from the form. The page also ships a strict Content-Security-Policy, so the browser itself blocks anything else.

Setup — how to run this page and let it talk to your bot
  1. Enable the freqtrade REST API ("api_server": {"enabled": true, …} with username/password) in your bot's config.
  2. Recommended — run this page locally. Download the file and open it straight from disk, or serve it from the same machine with python -m http.server, then point the form at http://127.0.0.1:8080. This works with plain-HTTP bots, needs no CORS setup, and the credentials you type never leave your machine.
  3. Or host the page publicly (e.g. GitHub Pages) and allow that origin. Browsers enforce CORS: add the page's exact origin (no trailing slash) — https://YOURNAME.github.io — to CORS_origins in the api_server block and restart the bot: 
    "api_server": {
    "enabled": true,
    "listen_ip_address": "127.0.0.1",
    "listen_port": 8080,
    "username": "freqtrader",
    "password": "…",
    "CORS_origins": ["https://YOURNAME.github.io"]
}
    Keep in mind: an HTTPS page cannot reach a plain-HTTP bot at all (no CORS entry fixes that — the local option above is the answer), the entry grants every page on that origin access to the bot API — not just this tool — and it should be removed again once the report is exported.
  4. Trust and TLS. These credentials give full control of the bot — the same API also exposes forceexit and stop — so treat the origin you put in CORS_origins as a standing trust decision and prefer running the page locally if you do not fully control that origin. Certificates must be valid: browsers reject self-signed ones and this page cannot skip verification (there is no --no-verify-tls in a browser), so self-signed setups should run the page locally or use a properly trusted reverse proxy.
What gets redacted?

Credentials and keys (any field whose name contains key, secret, token, password, chat, webhook or credential; the whole ccxt_config objects), exchange order/account identifiers, absolute money values (balances, stakes, costs, absolute PnL, funding fees, drawdown water marks) and personal/machine-specific values (bot name, local paths). Numeric redaction is fail-closed: a number is kept only when its key is recognized as safe, so fields freqtrade adds in the future are hidden until reviewed. Scale-invariant relative ratios are computed before redaction so the report stays useful without revealing the account size. Full field reference: tools/bot_report.md.

Dashboard image — what does it show instead of the absolute values?

After a successful export the page renders a freqUI-style dashboard snapshot that is safe to share as a PNG/SVG image. Every absolute-money field is replaced by a scale-invariant relative value, so the account size cannot be derived from the image:

  • Balance column → total return vs the start in % (profit_all_ratio: closed + open trades, exactly as /profit reports).
  • Absolute profit (e.g. -19.37% (-51.882)) → % only: closed profit vs the start, open-trade impact (realized grind exits + unrealized) vs the current balance.
  • Amount / stake amount columns → stake as % of the account at entry time; Currently deployed is open collateral (sum of open stake_amount) vs the current balance — not /count total_stake, which is open notional and exceeds collateral by the leverage factor on futures.
  • Profit over time → relative profit % per day/week/month plus trade count (no absolute axis).
  • Cumulative profit → cumulative closed profit vs the start: each trade's account impact rescaled by the balance history, so the curve lands on the closed-profit headline within rounding; dotted tip lands on the total return including open trades (red = loss, green = profit). With a closed-trades window the curve and headline are windowed; without daily coverage it falls back to summed impacts (labeled).
  • Wallet history → indexed equity (start = 100) from realized history, with a dotted tip to the total return so open trades are included without drawing the cliff as a solid move.
  • Watermark → the image footer reads Generated by plus the page URL as provenance (switch it off with the Watermark checkbox). Pages opened from disk show a neutral label instead, so no local filesystem path leaks into the shared image.

The image is built exclusively from ratios, percentages, counts, market prices and dates. A relative-only audit runs before every render and its result is shown above the preview.
